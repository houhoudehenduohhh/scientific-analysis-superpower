# Proposal 阶段规则

Proposal 只负责讨论研究目标、源数据、边界和算法方向，并生成当前版本的 Build Plan 与 Task MD。它不生成代码、不运行正式分析、不进行审计。

## 输出

```text
specs/
└── proposal-01-<主题>/
    ├── build_plan_p01.md
    └── tasks/
        └── task-01/
            └── task-01.md
```

新一轮直接在 `specs/` 下创建 `proposal-<序号>-<主题>/`。Build Plan 文件名用 `build_plan_p<序号>.md`，与本轮目录使用同一序号，并在功能单元内保持唯一。Harness 按该文件名定位 SDD 工作区。Task MD 放在本轮的 `tasks/` 下，由本轮计划用相对路径索引。

Build Plan 记录目标、源数据、算法概括、拟得到的输出、项目目录结构、任务清单、Runtime 执行图和阶段性验收节点。Task MD 记录一个任务的目的、边界、输入、脚本、输出、验收条件、验证证据和上下游影响。

## 执行顺序

1. 确定一个最小功能单元，再按「Proposal 轮次与修订」确认本轮的规格写入位置。
2. 与用户讨论目标、源数据、边界、算法方向和输出。
3. 按模板生成或更新 Build Plan，在「目标与边界」写明 `功能单元 Git 根目录` 的绝对路径。若用户给的是上层目录，定位本轮实际开发的子目录。
4. 按模板生成本轮 Task MD，并在 Build Plan 中索引。任务清单、Runtime 执行图和验收节点只登记本轮任务、步骤及节点。前轮 ID 用于追溯链接，跨轮产物在本轮作为输入说明。若承接前轮，在 Build Plan「目标与边界」汇总继承依据、本轮变化和重验范围。在关联 Task MD「上下游影响」链接具体的前轮 Proposal／Task、复用产物及对应验收记录，保留现有下游影响说明。复用前核对产物和验收状态，仍待验收的产物保持待验收。Building 收尾准备本轮 Runtime 合同时，把已验收并获准复用的前轮产物登记为合同输入，随合同一起接受 Building Audit。
5. 运行 Harness 的 `verify-build-plan` 和带 `--build-plan BUILD_PLAN` 的 `verify-task-spec`。验明全部索引任务、AC、结构化路径和依赖图。按「阶段性验收节点」表划分批次时，保留后续批次的 Task Spec 草案，先提交当前批次的具体规格和整体路线。
6. 检查任务依赖、接口、AC 和 Runtime 步骤图无环。
7. 呈现文件、版本编号、校验结果和将初始化或复用 Git 的绝对路径，等待用户批准。更换该路径属于计划实质变更，须重新批准。

## 路径及验收节点

- 在 Build Plan 的「项目目录结构」声明 `- path_schema: 1`，用主入口表为每个任务登记路径和新增、既有或迁移类型。每个 Task MD 用「主入口路径」字段写同样的路径。无主入口的任务也须明确声明。
- 新增或迁移的主入口及新增分析实现模块使用 `scripts/build/`。迁移时记录受影响的调用方。配置、pytest、冒烟入口与日志分别使用 `scripts/config/`、`scripts/pytest/`、`scripts/smoke_test/` 和 `scripts/logs/`。
- 在 Build Plan 的「拟得到的输出」表填 `results/data/`、`results/plot/` 或 `results/smoke_test/` 下的逻辑文件路径。把读者需要的分组和文件名写入路径。运行与执行轮次的标识由 Harness 登记。
- 所有节点各自通过节点审计。全部节点获接受后开展独立全链条审计，包括只有一个节点的计划。
- 新计划的校验及初始化须通过结构化路径检查。已初始化且仍绑定同一批准版本的旧工作区可以恢复。旧计划若尚未初始化，使用当前结构补齐并取得对应版本批准。

## 门禁

只有当前 Build Plan 与本轮 Task MD 均通过 Harness 格式校验，并获得用户明确批准后，才能进入 Building。Proposal 期间只读检查仓库状态，Git 初始化留在 Building。

## Proposal 轮次与修订

- 本轮草案尚未批准且未被 Harness、审计或运行记录引用时，在原目录更新 Build Plan 和 Task MD，只保留一份待审版本。
- 在同一轮内实质修改研究目标、源数据资格、概念算法、统计方法、关键假设或结论边界时，返回 Proposal 并重新取得受影响范围的批准。已批准或被流程引用的版本先保留对应快照及引用。已绑定状态按现有流程登记返工。当前状态支持返回 Proposal 时，经用户批准新版后用 `proposal-rebind` 重新绑定。若当前门禁无法登记返回，保留原绑定并报告阻断。尚未绑定的批准版本保留原批准证据，新版批准后按正常入口初始化。仅修改代码实现时返回 Building。
- 前轮完成后开展可独立审批的补充研究时，新建下一轮 Proposal，延续功能单元的普通 Task 编号。前轮任务通过规格链接承接。恢复旧计划时按已绑定的路径和编号读取，包括历史 `-EXT` 任务。
