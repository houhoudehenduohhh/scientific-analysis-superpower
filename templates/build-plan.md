## 拟创建的脚本结构

先确定预计创建或修改的文件、模块职责和接口，再切分任务。`build/` 内部按实际任务细分。

```text
scripts/
├── build/                        # 主脚本；内部结构按本次实现自行规划
├── config/                       # 配置和配置指纹
├── pytest/                       # pytest 测试代码与必要的测试记录
├── smoke_test/                   # 小样本运行脚本与验证入口
└── logs/                         # 正式日志；runtime/ 子目录存临时运行状态
```

这五个一级目录是脚本区的统一边界；具体脚本树是本次规划结果，不是固定模板。`scripts/smoke_test/` 存验证代码，`results/smoke_test/` 存验证结果。PID、进度和恢复状态共用 `scripts/logs/runtime/`，结束后按运行规则清理。

## Runtime 执行图与阶段性验收节点

此处规划**运行步骤**，与上面的 Build Task 分开编号；一个 Task 可实现多个运行步骤，多个 Task 也可共同形成一个验收成果。先列步骤，再按用户希望分批验收的成果划节点。发布、计算、回收等同一 Build Task 的不同操作分别列步骤，不因编号相同画出依赖回环。

| 运行步骤 ID | 对应 Build Task | 必须先完成的步骤或已接受节点 | 本步输入、输出及隔离写入位置 | 可并行的步骤／互斥条件 | 完成检查 |
|---|---|---|---|---|---|
| R01 | T01 | 无 |  |  |  |

| 验收节点 ID | 节点目的与包含的运行步骤 | 前置节点 | 阶段性成果与验收条件（引用 AC） | 用户授权范围与未纳入工作 |
|---|---|---|---|---|
| M01 | R01 | 无 |  |  |

自检：步骤及节点依赖必须是有向无环图；每步的前置产物已在本节点产生或来自身份可核验的已接受节点；并行步骤不得写同一可变产物。每项 Runtime AC 归属一个验收节点，所有目标输出最终被覆盖。失败重试是同一步的新尝试，不作为依赖回边。节点边界和顺序的实质改变须更新本计划并重新获用户批准。最后一个节点通过后仍需独立的全链条结果审计。
