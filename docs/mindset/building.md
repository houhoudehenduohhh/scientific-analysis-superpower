# Building 阶段

## 职责

将已批准的 Proposal 转换为可测试、可审查、可复现的代码实现。

## 核心思考

- 如何执行并验证 Build Plan 中的独立任务；
- 每个任务的输入、输出和失败条件是什么；
- 哪些行为需要测试先行；
- 如何避免代码实现偷偷改变科学方案；
- 如何记录任务进度和验证证据。

## 主要方式

执行 Proposal 中已批准的 `build_plan.md`。每个任务围绕一个可观察行为和一个主要风险。高风险数据和算法任务采用：

```text
失败测试 → 最小实现 → 测试通过 → 回归验证
```

按依赖顺序从 Build Plan 提取单个任务，生成 task brief，派给实现 Subagent。简报列出本任务的文件、接口、验收断言、失败条件及适用的科学约束。任务实现和修复分别提交 Git，以确定每次审查的差异范围。

独立 Reviewer 根据任务简报、实现报告、差异和测试证据，分别判断契约合规和代码质量。可复现的行为缺陷先用失败测试固定，再修复、重测和复审。两项均通过后关闭任务。

全部任务通过后执行适用的语法、导入和全量回归检查。有运行入口的功能单元用隔离的小样本验证入口、关键输出和预期结果。证据随 Build Plan 交给一名独立的最终 Reviewer，形成 Building Audit 报告。

## 测试与运行记录

- 主脚本放在 `scripts/build/`，内部按本次任务自行细分；
- pytest 测试代码和必要的测试记录放在 `scripts/pytest/`；
- 小样本运行脚本放在 `scripts/smoke_test/`，产物放在 `results/smoke_test/`；
- 通用配置和配置指纹放在 `scripts/config/`；
- Build 日志放在 `scripts/logs/`；
- 临时预览、一次性脚本和临时表格放在临时目录，任务完成后清理；
- 测试结果不作为正式科学结果写入 `results/data/`。

## 主要产物

- Build Plan 中补记的执行证据；
- 代码、配置和测试；
- Spec-to-code 映射；
- 任务验证记录。

## 门禁

代码能够被独立审查，任务测试和整体检查完成后，停止进入 Building Audit。Building 不生成正式研究结果。
